# 문제1: 테스트 자동화 전략 설계

## 시나리오 요약
배달의민족 앱에 "실시간 주문 현황" 화면 추가. 개발자 2명, 2주 후 오픈, 기존 자동화 없음.

---

## 1-1. 자동화 전략 수립

### 자동화 대상과 수동 유지 대상 구분

#### 자동화 대상

| 레이어 | 항목 | 판단 이유 |
|--------|------|-----------|
| API | 주문 상태 조회 (정상/에러) | 반복 실행 빈도 높음, 실행 속도 빠름 |
| API | 상태 전환 흐름 (접수 대기 → 조리 중 → 배달 중 → 완료) | 회귀 시 조기 감지 가능, 구현 비용 낮음 |
| API | 동시 요청 처리 및 에러 응답 (400/404/500) | 비즈니스 로직 검증 핵심 |
| E2E | 핵심 Happy Path (앱 실행 → 주문 현황 진입 → 상태 확인) | 릴리즈마다 반복 검증 필요 |
| E2E | 상태 변경 시 화면 실시간 갱신 확인 | 사용자 영향 직결 |

#### 수동 유지 대상

| 항목 | 판단 이유 |
|------|-----------|
| 실시간 Push 알림 UX (타이밍, 진동, 사운드) | 기기별 편차 크고, 자동화 대비 비용 과다 |
| 네트워크 불안정 / 앱 백그라운드 전환 시 동작 | 환경 재현이 어렵고 자동화 안정성 낮음 |
| 첫 릴리즈 전 탐색적 테스트(ET) | 명세에 없는 엣지 케이스 발굴은 사람이 유리 |
| 접근성(a11y) 검증 | 툴 지원 한계, 맥락적 판단 필요 |

---

### 테스트 피라미드 설계

```
         ▲
        /E2E\         10% — 핵심 플로우 1~2개 (Happy Path)
       /------\
      / API통합 \      70% — 상태 전환, 에러, 동시성
     /----------\
    /  단위(Unit)  \   20% — 상태 파싱 로직, 데이터 변환 (개발자 영역)
   /--------------\
```

**배분 이유:**

- **Unit (20%)**: 개발자가 작성하는 상태 변환 로직, JSON 파싱 등. QA가 직접 작성하기보다 코드 리뷰로 확인.
- **API Integration (70%)**: 가장 ROI가 높은 레이어. 실행 속도 빠르고(수십 ms), UI 변경에 영향 없이 안정적으로 동작. "실시간 주문 현황"의 핵심인 상태 전환 로직과 데이터 정합성은 여기서 검증.
- **E2E (10%)**: UI까지 포함한 최종 확인. 2주 일정 내에는 핵심 플로우 1~2개만. 이후 기능이 안정화되면 점진적으로 확대.

---

### 자동화 ROI 판단 기준

아래 3가지를 기준으로 자동화 여부를 결정합니다.

**1. 반복 실행 빈도**
- 매 배포마다 실행해야 하는 회귀 케이스 → 자동화 우선
- 1회성 검증(특정 버그 재현) → 수동

**2. 안정성**
- UI는 기획/디자인 변경으로 locator가 자주 깨짐 → 유지 비용 과다
- API는 명세가 명확하면 안정적 → ROI 높음

**3. 구현·유지보수 비용 대비 절감 시간**
- `(테스트 케이스 1회 수동 실행 시간) × (스프린트당 실행 횟수)` > `구현 시간 + 유지보수 시간` 이면 자동화
- 예: 주문 상태 API 5개 케이스 × 수동 3분 × 주 3회 실행 = 주 45분 절감. 구현 4시간이면 약 6주 후 손익 분기.

**2주 오픈 일정 내 우선순위:**
1. API 통합 테스트 먼저 구현 (속도 빠름, 안정적)
2. E2E는 Happy Path 1개로 시작, 이후 확장
3. UI 시각적 회귀 테스트는 안정화 이후로 연기

## 1-2. 파이프라인 통합

### CI/CD 단계별 실행 설계

```
개발자 PR 생성
    │
    ▼
[Stage 1] PR 검증 (pre-merge) ← 목표: 5분 이내 완료
    ├── 단위 테스트 (Unit)
    └── API 통합 테스트 (핵심 케이스)
         → 실패 시 머지 블로킹
    │
    ▼
main 브랜치 머지
    │
    ▼
[Stage 2] 스테이징 배포 후 (post-merge)
    ├── API 전체 회귀 테스트
    └── E2E 핵심 플로우 (Happy Path)
         → 실패 시 Slack 알림, 배포 보류
    │
    ▼
[Stage 3] 릴리즈 전 (pre-release)
    └── 전체 회귀 + E2E 확장 케이스
         → 실패 시 릴리즈 블로킹
```

**설계 의도:**
- Stage 1은 속도 우선 — 개발자 피드백 루프를 최소화하기 위해 빠른 API 테스트만 실행
- Stage 2는 안정성 우선 — 실제 스테이징 서버에서 E2E 실행, 환경 의존성 있는 케이스 여기서 처리
- E2E는 pre-merge 블로킹에서 제외 — 실행 시간(수 분)이 개발자 생산성을 저해하지 않도록

### Flaky 테스트 대응 정책

#### 1. 감지 및 격리

- CI에서 동일 테스트가 **3회 실행 중 1회 이상 불일치 결과**를 낼 경우 Flaky로 분류
- `@flaky` 태그 추가 후 **별도 suite(flaky-suite)로 격리** — main 파이프라인에서 제거해 블로킹 방지
- 격리 즉시 담당자 지정 및 Jira/GitHub Issue 등록

#### 2. 재시도 정책

- CI에서 **최대 2회 재시도** 허용
- 2회 재시도 후에도 실패 → 진짜 실패로 판단, 알림 발송
- 재시도로 통과한 케이스는 자동으로 Flaky 후보 목록에 기록

#### 3. 원인 분석 순서

```
1. 실패 증거 수집
   └── 스크린샷, 로그, 네트워크 타임라인 자동 첨부 (Playwright trace 등)

2. 재현율 측정
   └── 동일 케이스 10회 연속 실행 → 실패 횟수 기록
       재현율 30% 미만 → 환경/타이밍 문제 의심
       재현율 70% 이상 → 로직/명세 문제 의심

3. 원인 유형 분류
   ├── 타이밍 문제: 비동기 대기 전략 개선 (명시적 wait 조건 추가)
   ├── 테스트 간 의존성: 테스트 격리 (독립적인 fixture 사용)
   ├── 환경 불안정: 스테이징 서버 상태 확인, 목(Mock) 교체 검토
   └── 명세 변경: 실제 버그인지 스펙 변경인지 개발자와 확인

4. 수정 기한
   └── 2주 내 미수정 시 해당 케이스 비활성화 (skip) + 수동 대체
```

#### 4. 예방 원칙

- 테스트는 **독립적으로 실행 가능**해야 함 (공유 상태, DB 의존성 최소화)
- `Thread.sleep()` 같은 하드코딩 대기 금지 — 조건 기반 명시적 대기 사용
- 실패 시 충분한 증거가 남도록 CI에서 artifact(로그, 스크린샷) 자동 저장 설정
