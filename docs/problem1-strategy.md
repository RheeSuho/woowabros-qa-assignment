# 문제1: 테스트 자동화 전략 설계

## 시나리오 요약
배달의민족 앱에 "실시간 주문 현황" 화면 추가. 개발자 2명, 2주 후 오픈, 기존 자동화 없음.

---

## 1-1. 자동화 전략 수립

### 자동화 판단 기준

자동화 여부는 아래 3가지 기준으로 판단합니다.

**1. 반복 실행 빈도**
- 매 배포마다 실행해야 하는 회귀 케이스 → 자동화 우선
- 1회성 검증(특정 버그 재현, 탐색적 테스트) → 수동

**2. 실패 감지 가치**
- 놓쳤을 때 사용자 영향이 큰 케이스 → 자동화 우선
- 기기별 편차가 크거나 사람의 감각적 판단이 필요한 케이스 → 수동

**3. ROI (자동화 투자 대비 효과)**
- **본전 기준:** `구현 시간 ÷ (1회 수동 실행 시간 × 주간 실행 횟수)` = 몇 주 후 본전인지
- 예: 구현 4시간, 수동 실행 20분, 주 2회 반복 → `4h ÷ (20min × 2회)` = **6주 후 본전**
- 6주 이내 본전이 나오면 자동화, 그 이상이면 비용 대비 효과 재검토

---

### 테스트 피라미드 설계

과제 요구사항인 UI / API / E2E 3개 레이어로 설계합니다.

```
           ▲
          /E2E\         10% — 핵심 플로우 (Happy Path)
         /------\
        /   UI   \      20% — 화면 상태별 렌더링, 컴포넌트 검증
       /----------\
      /  API 통합  \    70% — 상태 전환, 에러, 동시성
     /--------------\
```

#### API 통합 (70%) — 최우선 구축

| 항목 | 판단 이유 |
|------|-----------|
| 주문 상태 조회 (정상/에러/없는 주문) | 핵심 비즈니스 로직, 실행 속도 빠름 |
| 상태 전환 흐름 (접수 대기 → 조리 중 → 배달 중 → 완료) | 회귀 시 조기 감지 가능 |
| 동시 요청 처리 및 에러 응답 (400/404/500) | 피크 타임 안정성 직결 |

UI 변경에 무관하게 안정적으로 동작하고 실행 속도가 빨라 ROI가 가장 높은 레이어입니다.

#### UI (20%) — 오픈 후 안정화 단계에서 구축

| 항목 | 검증 내용 |
|------|-----------|
| 화면 상태별 렌더링 | 로딩 스피너, 에러 화면, 빈 화면이 각 상황에 맞게 표시되는지 |
| 주문 상태별 UI | "접수 대기" / "조리 중" / "배달 중"의 텍스트·아이콘·색상이 정확한지 |
| 백그라운드 복귀 후 상태 갱신 | `device.pressHome()` 후 복귀 시 최신 상태로 갱신되는지 |

Espresso + ActivityScenario(ViewModel Mock)로 구현. 화면 단위로 격리해 실행하므로 E2E보다 빠르고 안정적입니다.

**2주 내 구축을 보류하는 이유:** 기존 자동화가 없는 상태에서 DI(의존성 주입) 기반 테스트 환경을 처음부터 구성하는 데 시간이 걸리고, 개발 중인 화면의 뷰 구조가 확정되기 전에 작성하면 유지보수 비용이 과다합니다.

#### E2E (10%) — 2주차에 1개 목표

| 항목 | 판단 이유 |
|------|-----------|
| Happy Path: 앱 실행 → 주문 현황 진입 → 상태 확인 (Android) | 릴리즈마다 반복 검증 필요 |

iOS XCUITest는 Android 안정화 이후로 연기합니다. 2주 일정에 두 플랫폼 동시 구축은 현실적이지 않습니다.

---

### 수동 유지 대상

| 항목 | 판단 이유 |
|------|-----------|
| Push 알림 진동·사운드·타이밍 | 기기별 편차 크고 자동화로 감각적 검증 불가 |
| 네트워크 불안정 시 UX (오프라인 배너, 재연결 처리) | 환경 재현 불안정, 자동화 안정성 낮음 |
| 첫 릴리즈 전 탐색적 테스트(ET) | 명세에 없는 엣지 케이스 발굴은 사람이 유리 |
| 접근성(a11y) 최종 검증 | 툴로 감지 가능한 항목은 보조 도구 활용, 맥락적 판단은 수동 |

---

### 2주 일정 내 우선순위

```
1주차: API 통합 테스트 구현 완료
2주차: E2E Happy Path 1개 (Android) 구현 + 전체 CI 연동
오픈 후: UI 레이어 구축, iOS E2E 추가
```

## 1-2. 파이프라인 통합

### CI/CD 단계별 실행 설계

```
개발자 PR 생성
    │
    ▼
[Stage 1] PR 검증 (pre-merge) ← 목표: 5분 이내
    └── API 통합 테스트 (핵심 케이스)
         → 실패 시 머지 블로킹
    │
    ▼
main 브랜치 머지
    │
    ▼
[Stage 2] 스테이징 배포 후 (post-merge)
    ├── API 전체 회귀 테스트
    └── E2E Happy Path (Android)
         → 실패 시 Slack 알림, 배포 보류
    │
    ▼
[Stage 3] 릴리즈 전 (pre-release)
    └── 전체 회귀 + UI 테스트 + E2E 확장
         → 실패 시 릴리즈 블로킹
```

**설계 의도:**
- Stage 1은 속도 우선 — API만 실행해 개발자 피드백 루프 최소화
- E2E는 pre-merge 블로킹 제외 — 실행 시간(수 분)이 개발 흐름을 막지 않도록
- UI 테스트는 화면 안정화 후인 Stage 3부터 포함

### Flaky 테스트 대응 정책

#### 1. 감지 및 격리

- CI에서 동일 테스트가 **3회 실행 중 1회 이상 불일치** 결과를 낼 경우 Flaky로 분류
- `@flaky` 태그 추가 후 **별도 suite로 격리** — main 파이프라인 블로킹 방지
- 격리 즉시 담당자 지정 및 이슈 등록

#### 2. 재시도 정책

- CI **최대 2회 재시도**, 로컬 1회
- 2회 재시도 후에도 실패 → 진짜 실패로 판단, Slack 알림
- 재시도로 통과한 케이스는 Flaky 후보 목록에 자동 기록

#### 3. 원인 분석 순서

```
1. 실패 증거 수집
   └── 스크린샷, logcat, 네트워크 타임라인 자동 저장 (CI artifact)

2. 재현율 측정
   └── 동일 케이스 10회 연속 실행
       재현율 30% 미만 → 환경·타이밍 문제 의심
       재현율 70% 이상 → 로직·명세 문제 의심

3. 원인 유형 분류
   ├── 타이밍: Thread.sleep 제거, 조건 기반 명시적 대기로 교체
   ├── 테스트 간 의존성: 격리 (독립적인 fixture, 상태 초기화)
   ├── 환경 불안정: 스테이징 서버 상태 확인, Mock 교체 검토
   └── 명세 변경: 실제 버그인지 스펙 변경인지 개발자 확인

4. 수정 기한
   └── 2주 내 미수정 시 비활성화(skip) + 수동 대체
```

#### 4. 예방 원칙

- 테스트는 독립적으로 실행 가능해야 함 (공유 상태, 실행 순서 의존 금지)
- 하드코딩 대기(`Thread.sleep`) 금지 — 조건 기반 명시적 대기 사용
- CI에서 실패 시 artifact(로그, 스크린샷) 자동 저장

## AI 도구 활용

본 문제는 **Claude Code** (Anthropic)를 활용해 작성했습니다.

| 단계 | 활용 내용 | 직접 결정한 부분 |
|------|----------|----------------|
| 전략 서술 | 테스트 피라미드 표현 정리, 표 형식 구조화 | UI/API/E2E 배분 비율, 수동 유지 대상 판단 |
| CI/CD 설계 | 3단계 파이프라인 다이어그램 표현 | Stage별 블로킹 기준, E2E를 pre-merge에서 제외하는 판단 |
| Flaky 정책 | 섹션 구조화 및 표현 다듬기 | 재시도 횟수(CI 2회/local 1회), 격리 기준 |

> 자동화 전략의 판단 기준과 우선순위는 실무 QA 경험을 바탕으로 직접 결정했으며, AI는 서술 표현과 문서 구조화에 활용했습니다.
