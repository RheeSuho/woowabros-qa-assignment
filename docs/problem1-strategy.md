# 문제1: 테스트 자동화 전략 설계 — 답안

## 먼저 상황 정리

이 문제를 풀기 전에 조건을 먼저 짚어봤습니다.

- 새로운 화면(실시간 주문 현황), 개발자 2명, **2주 후 오픈**
- 이 서비스에는 **자동화 테스트가 하나도 없음** (완전히 처음부터 시작)
- "실시간"이라는 특징 때문에 폴링이나 웹소켓처럼 화면이 계속 업데이트되는 방식일 가능성이 큼 → 타이밍 때문에 테스트가 불안정(flaky)해질 위험이 있음
- 개발이 이번 주부터 시작이라, 요구사항이나 UI가 스프린트 내내 계속 바뀔 가능성이 큼

→ 그래서 이 문제의 핵심은 **얼마나 많은 자동화를 이루어 내느냐**가 아니라, 짧은 기간 안에서 **자동화 대상을 구분하여 적절한 도구를 사용**하여 수행하는 것 이라고 생각했습니다.

---

## 1-1. 자동화 전략 수립

### 자동화할 것 vs 수동으로 남길 것, 판단 기준

아래 4가지 기준으로 나눴습니다.

| 기준 | 자동화하면 좋은 경우 | 수동으로 남기는 게 나은 경우 |
|---|---|---|
| **반복 빈도** | 배포할 때마다 계속 회귀 테스트해야 하는 핵심 기능 | 이번 스프린트에 한 번만 확인하면 되는 것 |
| **요구사항 안정성** | 이미 확정된 것 | 아직 계속 바뀌는 것 |
| **재현 가능성** | 같은 조건에서 항상 같은 결과가 나오는 것 | 네트워크 상태나 타이밍에 따라 결과가 달라지는 것 |
| **실패 시 임팩트** | 잘못되면 고객이 주문 상태를 잘못 보고 CS 문의가 늘어날 수 있는 것 | 문제가 생겨도 영향이 크지 않은 것 |

이 기준을 적용하기 전에 먼저 짚어둘 점이 있습니다. 이 화면이 네이티브인지 웹뷰 기반인지에 따라 적합한 자동화 도구가 달라지므로, 시작 전에 개발팀과 먼저 확인할 계획입니다. 다만 제가 강점을 가진 영역은 Web/Playwright 기반 자동화이기 때문에, 2주라는 기간에는 API 레이어 자동화에 역량을 집중하고 UI/E2E는 핵심 흐름만 스모크로 검증하는 방향이 현실적이라고 판단했습니다. 앱 UI 자동화 환경 구축은 이번 스프린트부터 병행 준비하겠습니다.

이 판단을 기준으로 나눠보면 **자동화 대상**과 **수동 대상**은 다음과 같습니다.

**자동화 대상**
- 주문 상태 전이 로직 (접수 → 조리중 → 픽업중 → 배달중 → 배달완료, 취소/지연 포함)
  - 화면이 아니라 API 레벨에서, 상태가 순서대로 올바르게 바뀌는지 확인
- 화면 핵심 흐름 1가지 (주문 후 화면 진입 시 상태값 렌더링 확인)
  - 상태값 자체가 맞는지는 API 테스트에서 이미 확인했으므로, 여기선 "화면에 잘 표시되나"만 보는 E2E 스모크
- 상태 변경 시 화면 반영 여부 — 대표 케이스 3개
  - Staging 배포 직후 실행하는 스모크 범위이며, 그 외 조합은 nightly 회귀에서 확인
  - 정상 흐름: 조리중 → 픽업중 → 배달중으로 바뀔 때 화면이 자동으로 갱신되는지
  - 지연 케이스: 예상보다 늦어질 때 지연 안내 문구가 뜨는지
  - 취소 케이스: 주문이 취소됐을 때 상태와 안내 문구가 바로 바뀌는지
 
**수동으로 남기는 것**
- UI 디자인, 버튼 위치, 문구
  - 스프린트 초반이라 계속 바뀌어서, 지금 자동화하면 바뀔 때마다 다시 고쳐야 해서 오히려 손해
- 네트워크 단절/재연결, 앱 백그라운드-포그라운드 전환
  - 매번 똑같이 재현하기 어려워서, 자동화하면 flaky의 주 원인이 되기 쉬움
- 디자인·사용성처럼 사람이 눈으로 판단해야 하는 부분

### 테스트 피라미드 관점의 배분

```
        E2E (10~15%)
      가장 중요한 흐름 1~2개만
     ─────────────────────────
    UI 컴포넌트 테스트 (20~25%)
    화면 상태별 렌더링 확인
    (로딩/에러/빈 상태/실시간 업데이트)
   ─────────────────────────────
  API/통합 테스트 (55~65%)
  주문 상태 전이, 실시간 데이터,
  취소/지연 같은 예외 케이스
 ───────────────────────────────────
Unit 테스트 (개발팀 영역)
```

- **API/통합 테스트에 가장 많이 투자하는 이유**: 이 화면의 핵심은 "주문 상태가 정확히 전달되고 정확히 표시되는가"입니다. 이건 UI에서 하나하나 확인하는 것보다 API 레벨에서 확인하는 게 훨씬 빠르고 안정적입니다.
- **E2E를 최소화하는 이유**: "실시간"이라는 특성상 타이밍 문제로 flaky가 발생할 위험이 구조적으로 큽니다. 2주 안에 E2E를 두껍게 쌓으면 오히려 테스트 신뢰도가 떨어질 수 있어, 핵심 흐름 1~2개로만 제한합니다.

### 자동화 ROI 판단 기준

이번 프로젝트는 자동화 자산이 전무한 상태에서 시작하므로, 단순 비용 절감뿐 아니라 **품질 안정화 속도**와 **향후 재사용성**을 함께 봐야 한다고 생각합니다.

**① 단기 기준 (이번 스프린트 내) — 안정성/리드타임**
- 지표 1: 회귀 테스트 시간 단축률 — 오픈 직전 코드 수정 시 수동 검증 대비 자동화 실행 시간이 얼마나 줄었는지 (목표: 80% 이상 단축)
- 지표 2: 코드 프리즈 기간 결함 조기 발견 수 — 오픈 직전 긴급 수정으로 인한 사이드 이펙트를 수동 QA보다 자동화가 먼저 잡아낸 건수

**② 장기 기준 (오픈 이후 운영) — 자산화 가치 (가장 중요)**
- 지표 3: 스크립트 재사용 빈도 — 이번에 만든 주문 현황 API 테스트가 다음 스프린트/업데이트에서 수정 없이 얼마나 반복 실행되는지
- 판단 수치: `아낀 수동 인건비 > 초기 구축 비용 + 유지보수 비용`을 만족하는 손익분기점이 6개월 이내면 ROI가 우수하다고 판단

실무에서는 이 기준을 아래 질문들로 단순화해서 판단합니다.
1. 이 시나리오가 앞으로 배포할 때마다 계속 반복 검증될 것인가? (그렇다면 자동화 우선순위 높음)
2. 요구사항이 아직도 계속 바뀌고 있나? (변동성이 크면 자동화를 미루는 게 나음 — 지금 만들면 계속 고쳐야 해서 오히려 손해)
3. 같은 조건에서 항상 같은 결과가 재현되는가? (네트워크나 타이밍에 따라 결과가 달라지는 영역은 자동화해도 flaky로 이어져 오히려 비용만 늘어남)
4. 실패했을 때 비즈니스 임팩트가 큰가? (CS 문의가 늘어날 만한 부분이면 우선순위를 높임)
5. 수동 실행 시간과 자동화 구축/유지 시간을 비교했을 때 뭐가 더 이득인가? (1회성 케이스는 아무리 중요해도 자동화가 오히려 손해일 수 있음)

결국 ROI가 좋다는 건 숫자 하나가 아니라 **QA가 안정된 영역은 자동화에 맡기고, 불안정한 영역에 집중할 수 있는 상태**에 도달했는지로 확인됩니다.

## 1-2. 파이프라인 통합

### 실행 단계 설계

| 단계 | 트리거 | 실행 대상 | 목적 | Gate 여부 |
|---|---|---|---|---|
| 1. PR 생성 시 | 코드 리뷰 요청 | Lint, Unit 테스트, 빠른 API 테스트 | 5분 이내 빠른 피드백 | Hard gate (실패 시 머지 차단) |
| 2. main 병합 시 | 병합 시점 | API/통합 테스트 전체 | 테스트 서버 대상, 병렬 실행 | Hard gate |
| 3. Staging 배포 후 | 배포 직후 | E2E 스모크 (핵심 흐름만) | 실제 앱/서버로 확인 | Hard gate |
| 4. Nightly | 매일 새벽 | 전체 회귀 + flaky 후보 재확인 | 시간 여유 있게 넓게 확인 | Soft gate (실패해도 바로 막지 않고 담당자가 확인) |

기본 원칙은 **"빠르고 안정적인 테스트는 앞단에서 배포를 막는 hard gate로 쓰고, 느리거나 불안정할 수 있는 테스트는 뒷단이나 야간으로 보낸다"**는 것입니다. 2주짜리 신규 기능에 무거운 E2E를 PR 단계마다 돌리면 개발 속도가 느려지고, 실패 원인 파악에 오히려 시간을 더 뺏길 수 있습니다.

### Flaky 테스트 대응 정책

**1) 판정 기준**
- 동일 커밋에서 재실행했을 때 결과가 달라지는 경우
- 최근 여러 번 실행한 것 중 성공/실패가 번갈아 나타나는 경우

**2) 격리(Quarantine)**
- Flaky로 판정되면 별도 태그로 분리해서 hard gate에서는 제외하되, 완전히 삭제하지 않고 nightly에는 계속 포함시켜 추적합니다.
- 격리된 테스트는 대시보드에 남겨서 "숨기는 것"이 아니라 "관리해야 할 부채"로 다룹니다.

**3) 재시도(Retry) 정책**
- 자동 재시도는 최대 1~2회로 제한합니다. 재시도로 통과해도 "정상 통과"가 아니라 "flaky로 기록"을 남깁니다.
- 재시도는 임시방편일 뿐이므로, 계속 이런 식으로 살아남는 테스트는 SLA(예: 1주일)를 정해 반드시 원인 분석하도록 합니다.

**4) 원인 분석**
Flaky 원인을 카테고리화해서 접근합니다.
- **타이밍/동기화 이슈**: 임의의 sleep 대신 명시적 상태 대기로 교체 — 실시간 화면 특성상 이 원인이 가장 많을 것으로 예상합니다.
- **테스트 데이터 오염**: 병렬 실행 시 같은 데이터를 건드려서 꼬이는 경우 → 테스트마다 독립된 데이터 사용
- **환경 문제**: 테스트 서버나 디바이스 불안정 → 인프라 이슈로 따로 기록
- **실제 버그**: 위 셋에 해당하지 않으면 실제 프로덕트 버그일 가능성 → 즉시 에스컬레이션

**5) 오너십**
- Flaky 테스트는 작성자(또는 담당 QA)가 SLA 내 조치하는 걸 원칙으로 하고, 장기 미해결 시 삭제를 검토합니다. 계속 실패해서 아무도 신뢰하지 않는 테스트는 자산이 아니라 부채입니다.

## 요약

- 2주·자동화 0에서 시작하는 신규 기능이라, **"어디까지 자동화하느냐"보다 "지금 자동화하면 안 되는 걸 구분하는 것"**이 더 중요하다고 판단했습니다.
- API 레이어에 자동화 투자를 집중하고, UI/E2E는 핵심 흐름 중심의 스모크로 최소화하며, 나머지는 의도적으로 수동 테스트에 남겨둡니다.
- 파이프라인은 "빠르고 안정적인 건 앞단 hard gate, 느리거나 불안정할 수 있는 건 뒷단/nightly"로 배치하고, flaky는 숨기지 않고 격리·추적·SLA 기반으로 관리합니다.
